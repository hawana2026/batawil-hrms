# BATAWIL HRMS — المرحلة الثانية: العمليات اليومية

تطبيق موارد بشرية عربي (RTL) بواجهة أصلية، وخادم Node.js/TypeScript، وقاعدة بيانات مركزية، ومصادقة وجلسات وصلاحيات ونطاق فروع وسجل تدقيق مركزي.

المرحلة الأولى أنجزت الأساس الأمني (الدخول، المستخدمون، الفروع، الأدوار، التدقيق). المرحلة الثانية تضيف العمليات اليومية: الموظفون، التحضير اليومي والشهري، الإجازات، السلف، التحويلات، الموظفون الجدد، الرواتب، الاعتمادات، والتقارير. أُضيف في 2026-10-26 ملف الموظف الشامل: مسميات وظيفية معتمدة، مدير مباشر مع منع الحلقات، عقود وظيفية، مستندات مصنّفة بتاريخ انتهاء، وسجل وظيفي دائم لكل تغيير.

هذه **نسخة تطوير محلية**، وتوجد نسخة عرض تجريبية منشورة على Render ببيانات وهمية فقط: https://batawil-hrms-demo-67236.onrender.com (الخطة المجانية وقاعدة Neon منفصلة بمخطط `batawil_demo` — ليست للإنتاج ولا لبيانات الموظفين الحقيقية). أُدخلت بيانات موظفين حقيقية محليًا بطلب صريح من المستخدم في 2026-10-25، لذا فإن `.data` والنسخ الاحتياطية وحزم التصدير تحتوي بيانات شخصية ويجب التعامل معها كبيانات سرية وعدم رفعها أو مشاركتها. لا ترفع قاعدة PGlite أو مجلد `.data` إلى الإنترنت؛ اتبع مسار النشر الإنتاجي الموثق أدناه.

## نطاق المرحلة الثانية المنفّذ

- **الموظفون والأقسام:** سجل مركزي مع بحث وتصفية وترقيم صفحات، إضافة وتعديل، عرض ملف الموظف، أرشفة بسبب وتاريخ بدل الحذف النهائي، أقسام، مرفقات، وطلب نقل وظيفي.
- **استيراد وتصدير الموظفين:** قالب Excel رسمي، تصدير Excel، واستيراد حتى 500 صف وحجم 5 ميجابايت. يُتحقق من كل الصفوف قبل الحفظ، ويُرفض الملف كاملًا عند وجود أي خطأ مع بيان الصفوف، ثم تُحفظ الصفوف الصحيحة في معاملة واحدة مع توليد الرقم الوظيفي تلقائيًا عند تركه فارغًا.
- **التحضير اليومي اليدوي:** كشف لكل فرع وتاريخ، الحالات الثماني (حاضر، غائب، إجازة، إذن، مهمة، راحة أسبوعية، تأخير، غياب بعذر)، أسماء مؤقتة لغير المسجلين، دقائق التأخير وساعات العمل والأسباب، تعديل جماعي، حفظ تلقائي للمسودة، عدادات المسجل وغير المسجل، ثم إرسال واعتماد وإعادة بملاحظة.
- **تصحيح التحضير المعتمد:** تصحيح صف مع سبب إلزامي مع الاحتفاظ بعدد التصحيحات ومن قام بها في التدقيق.
- **ربط الإجازات بالتحضير اليومي:** الطلبات المعتمدة تؤثر في كشوف التحضير المسموح تعديلها، وتُملأ صفوف الموظفين غير المسجلين تلقائيًا بحالة الإجازة أو الإذن في الكشف اليومي والتصدير.
- **التحضير الشهري:** يُشتق من التحضير اليومي لشهر كامل (28–31 يومًا) بالرموز ح/غ/إ/ذ/م/ر/ت/ع، مع تجاوز يدوي لأي يوم وملاحظة، وتأكيد الأيام الناقصة قبل الاعتماد، وحالة كشف شهرية، وإرسال واعتماد وإعادة.
- **متابعة الفروع:** شاشة تعرض تغطية التحضير لكل فرع في الشهر، الأيام المغطاة والناقصة، وحالة الكشف، وآخر إرسال، مع انتقال مباشر إلى تحضير اليوم.
- **الإجازات والأذونات:** إنشاء وإرسال واعتماد أو رفض بسبب، منع التداخل، الإلغاء، وربط الاعتماد بالتحضير والإشعارات.
- **السلف المالية:** دورة الموارد البشرية ثم المالية، صرف، وسجل حركات (صرف واستقطاع) مع منع تجاوز المتبقي، وتسجيل الاستقطاعات اليدوية.
- **ربط الرواتب بالسلف:** عند اعتماد سجل راتب تُسجَّل حركة استقطاع مرتبطة بسجل الراتب موزعة على السلف المصروفة الأقدم أولًا، مع قيد فريد يمنع التكرار.
- **التحويلات الوظيفية:** طلب نقل بين الفروع، اعتماد بتاريخ سريان يحدّث فرع الموظف مع الحفاظ على بيانات الحضور التاريخية، ورفض أو إلغاء.
- **الموظفون الجدد:** طلب تعيين واعتماد ينشئ الموظف مرة واحدة داخل معاملة واحدة ويسجل المعتمد.
- **الرواتب وبيانات الاستحقاق:** توليد أو تحديث شهري من الراتب الأساسي وملخص الحضور والإجازات ورصيد السلف، بدلات وخصومات وخصم سلف يدوية ضمن الحدود، حالات مسودة/تمت المراجعة/معتمد، وقفل السجل نهائيًا بعد الاعتماد.
- **الاعتمادات والطلبات:** صندوق موحد لكل أنواع الاعتماد مع التفاصيل والمرفقات والسجل، إضافة إلى أزرار الاعتماد داخل كل وحدة.
- **التقارير والطباعة:** الغياب اليومي والشهري، الأكثر غيابًا، التأخير، أيام العمل، سجل موظف، ومقارنة الفروع، مع تصدير Excel وتدقيق عمليات التصدير.
- **الإشعارات وسجل التدقيق وإعدادات النظام:** إشعارات داخلية لكل مستخدم، سجل تدقيق مركزي غير قابل للتعديل من التطبيق، إعدادات اسم الشركة والعملة وتذييل الطباعة وأوقات العمل والسماحية وأيام الراحة، وإدارة الأقسام.
- **الصلاحيات:** سبع وثلاثون صلاحية موزعة على الأدوار، وعزل بيانات الفروع في القراءة والكتابة، وقائمة تنقل تُبنى حسب الصلاحيات بالترتيب المطلوب.
- **الحذف الإداري المنضبط:** صلاحية `records.delete` لمدير النظام فقط، وواجهة حذف نهائي في شاشات الموظفين والأقسام والفروع والمستخدمين والإجازات والسلف والتحويلات والموظفين الجدد والتحضير اليومي والشهري والرواتب. يمنع الخادم حذف أي سجل مرتبط بسجلات أخرى، ويُنظّف المرفقات وطلبات الاعتماد، ويسجّل كل حذف في التدقيق. حذف المستخدم حذف ناعم يحافظ على سجل التدقيق ويُلغي جلساته وارتباطاته بالفروع.

### ملف الموظف الشامل (2026-10-26)

- **المسميات الوظيفية المعتمدة:** جدول `job_titles` مرتبط بالأقسام، إدارة من نافذة «المسميات الوظيفية» (إضافة، إعادة تسمية تُحدّث موظفيها، تعطيل يمنع الاختيار الجديد). يبقى حقل المسمى النصي الحر متاحًا كحل احتياطي.
- **المدير المباشر:** عمود `manager_id` مع تحقق الخادم من وجود المدير ونشاطه وكونه في نفس الفرع، ومنع اختيار الموظف لنفسه، ومنع الحلقات الدائرية عبر استعلام تكراري.
- **العقود:** جدول `employee_contracts` بأنواع دائم/محدد/تجربة/جزئي وحالة نشط/منتهٍ/ملغى، عقد نشط واحد لكل موظف (فهرس فريد جزئي)، تحقق من تواريخ البداية والنهاية، ومزامنة الراتب الأساسي تلقائيًا عند تفعيل العقد.
- **المستندات:** رفع ملفات مع عنوان ونوع (عقد، هوية وطنية، شهادة، تقرير طبي، آخر) وتاريخ انتهاء، وإمكانية تعديل البيانات الوصفية، مع بقاء التحقق من النوع والحجم والصلاحيات كما هو.
- **السجل الوظيفي الدائم:** جدول `employee_history` يسجّل التعيين وتعديل البيانات وتغيير الحالة والراتب والنقل والعقد والمستند والأرشفة مع تفاصيل وتاريخ سريان ومن قام بالعملية، ويُعرض في تبويب «السجل الوظيفي».
- **الأرشفة الكاملة:** أرشفة الموظف تغلق عقده النشط وتكتب سجل أرشفة داخل معاملة واحدة، وتبقى تعديلات الملف والعقود مرفوضة بعد الأرشفة (409).
- **الواجهة:** ملف الموظف أصبح تبويبات: البيانات الأساسية، العقود، المستندات، السجل الوظيفي، التحويلات — مع أزرار إضافة/تعديل عقد، رفع/تنزيل/تعديل/حذف مستند، وإدارة المسميات.

## غير المنفّذ أو غير المكتمل

- النسخة العامة الحالية على Render هي **عرض تجريبي ببيانات وهمية فقط** على خطة مجانية وقاعدة Neon منفصلة (`batawil_demo`). لا تُستخدم لبيانات موظفين حقيقية.
- لم يُختبر النسخ الاحتياطي والاستعادة على PostgreSQL الإنتاجي فعليًا؛ السكربتات جاهزة وتُختبر على الخادم بعد النشر.
- PostgreSQL الإنتاجي مدعوم في الكود عبر `pg`، لكن جميع الاختبارات وجولة التصدير والاستيراد جرت على PGlite المحلية.
- لا توجد رسائل بريد أو SMS، ولا استعادة كلمة مرور عبر البريد، ولا SSO أو MFA.
- لا توجد خدمة ذاتية للموظف تتجاوز شاشة الحساب الشخصي.
- لا يوجد محرر أدوار مخصص؛ مصفوفة الأدوار للعرض، وإسناد الأدوار يتم من شاشة المستخدمين.
- الحذف النهائي متاح لمدير النظام فقط عبر صلاحية `records.delete`، ومقيّد بفحص الارتباطات في الخادم؛ المسار الافتراضي لبقية الأدوار يظل الأرشفة والإلغاء.
- الرواتب تغطي الراتب الأساسي والبدلات والخصومات وخصم السلف فقط. لا توجد ضريبة دخل أو تأمينات اجتماعية أو مكافأة نهاية خدمة أو أرشيف قسائم رواتب أو تحويل بنكي.
- لا يوجد منع عام للاعتماد الذاتي: المستخدم الذي يجمع صلاحية الإنشاء وصلاحية الاعتماد (مثل مدير النظام) يستطيع اعتماد طلب أنشأه بنفسه. افصل الأدوار في التشغيل الفعلي، وهذه فجوة مفتوحة للمرحلة التالية.
- المرفقات تُخزّن داخل قاعدة البيانات بحد 2 ميجابايت، وليست في تخزين كائنات خارجي.
- تنسيقات الطباعة A4 أفقية/رأسية موجودة وتُحقن عند الطباعة، لكن لم يُختبر حوار الطباعة الفعلي أو طابعة حقيقية آليًا.
- اختُبرت واجهة المرحلة الثانية يدويًا على سطح المكتب؛ لم يُعد اختبار الاستجابة على الجوال بعد كل تغييرات المرحلة الثانية.

## البنية

```text
public/                         واجهة SPA عربية RTL بدون موارد CDN خارجية
  js/app.js                     الإقلاع، الدخول، الهيكل، التوجيه، التنقل حسب الصلاحيات
  js/core.js                    أدوات DOM، النوافذ، التنبيهات، طلبات API
  js/hr-common.js               مكونات الموارد البشرية، الحالات، الطباعة، النماذج
  js/views/                     شاشات المرحلتين الأولى والثانية
server/src/
  app.ts                        Express، Helmet/CSP، حارس المصدر، حدود الطلبات
  auth/                         كلمات المرور، الجلسات، الصلاحيات
  middleware/                   المصادقة، الصلاحيات، حارس المصدر
  routes/                       public, auth, meta, dashboard, users, branches, roles, audit,
                                employees, departments, attendance, leaves, advances, transfers,
                                new-hires, payroll, approvals, reports, attachments, settings, notifications
  services/                     نطاق الفروع، قرارات الاعتماد، الإشعارات، إعدادات النظام، الموظفون
  lib/                          التدقيق، الأخطاء، Excel، المخططات، المعرفات
  db/                           محرك PGlite/PostgreSQL وترحيلات
  cli/                          migrate, setup-admin, reset-admin, demo-seed
migrations/                     001–010
server/tests/                   اختبارات API والأمان والموارد البشرية (PGlite في الذاكرة)
```

- في التطوير المحلي: PGlite مدمجة داخل العملية في `./.data/pglite`، وتسمح بعملية واحدة فقط على ملف قاعدة البيانات.
- في الإنتاج: PostgreSQL حقيقي فقط. التطبيق يرفض PGlite عندما `NODE_ENV=production`.
- الجلسة في ملف تعريف ارتباط `httpOnly` باسم `batawil_session`، والبيانات التجارية لا تُحفظ في المتصفح.
- كل طلب API يقرأ المستخدم والدور والفروع من قاعدة البيانات، لذا يسري تغيير الصلاحيات فورًا.

## المتطلبات والتشغيل المحلي

- Node.js 20.19 أو أحدث (تم التطوير والاختبار على Node 24).
- npm 10 أو أحدث.
- PostgreSQL 15+ في الإنتاج (لم يُستخدم في بيئة المراجعة).

```bash
npm install
cp .env.example .env
npm run migrate
npm run setup
npm run dev
```

- `npm run setup` ينشئ أول مدير نظام فقط عندما لا يوجد أي مستخدم. إذا تركت `ADMIN_PASSWORD` فارغًا، تُولّد كلمة مرور مؤقتة قوية وتُطبع **مرة واحدة** في الطرفية.
- سيُطلب تغيير كلمة المرور المؤقتة عند أول دخول.
- إذا فُقدت كلمة مرور مدير النظام، أوقف الخادم ثم:
  ```bash
  npm run reset-admin -- --username admin
  ```
  يولّد كلمة مرور مؤقتة تُطبع مرة واحدة، ويُلغي جلسات الحساب، ويُلزم بتغييرها عند الدخول.
- الرابط المحلي الافتراضي: `http://localhost:3000`.
- لا توجد بيانات دخول افتراضية. لا تضع كلمات مرور حقيقية في `.env` أو في مستودع مشترك.
- `npm run seed:demo` اختياري لبيئة التطوير فقط ومرفوض في الإنتاج. بيانات العرض التي يزرعها هذا الأمر وهمية، وتختلف عن استيراد كشف أكتوبر 2026 الحقيقي المحلي الموضح أدناه.
- `.env` و`.data` مستبعدان من Git. لا تنقل قاعدة PGlite التطويرية إلى الإنتاج، ولا تشارك نسخها الاحتياطية لأنها تحتوي بيانات موظفين حقيقية.

أوامر مساعدة:

```bash
npm run typecheck     # فحص TypeScript بدون إخراج
npm test              # 44 اختبارًا آليًا على قاعدة PGlite في الذاكرة
npm run build         # بناء الخادم إلى dist/
npm start             # تشغيل المخرجات المبنية
```

## الأدوار والصلاحيات

| الدور | المفتاح | الملخص في المرحلة الثانية |
| --- | --- | --- |
| مدير النظام | `admin` | كل الصلاحيات وكل الفروع |
| مدير الموارد البشرية | `hr_director` | عمليات الموارد البشرية كاملة، اعتماد الحضور والإجازات والتحويلات والموظفين الجدد، اعتماد السلف من الموارد البشرية، الرواتب، التقارير، الإعدادات |
| موظف شؤون الموظفين | `hr_officer` | إدخال وإدارة الموظفين والحضور والإجازات والتحويلات والموظفين الجدد والسلف والرواتب، دون صلاحيات الاعتماد باستثناء ما يمنحه `payroll.manage` من مراجعة واعتماد سجلات الرواتب |
| المدير التنفيذي | `executive` | اطلاع للقراءة على الوحدات والتقارير وصندوق الاعتمادات |
| مدير الفرع | `branch_manager` | عمليات فرعه: الحضور والإجازات والتحويلات والموظفون الجدد والسلف والتقارير، وإرسال الطلبات دون اعتمادها |
| المدير المباشر | `direct_manager` | تحضير وإرسال الطلبات ضمن نطاقه دون إدارة الفروع |
| مسؤول الإدارة المالية | `finance` | اعتماد السلف المالي، الصرف والاستقطاعات، الرواتب، والتقارير |
| الموظف | `employee` | الحساب الشخصي فقط |

قواعد أساسية:

- تُطبَّق صلاحيات الوحدة ونطاق الفروع على الخادم، لا على إخفاء عناصر الواجهة فقط.
- لا يمكن منح دور يتجاوز صلاحيات المانح، ولا إسناد مستخدم إلى فرع خارج نطاقه، ولا منح «كل الفروع» إلا لمن يملكه.
- تعطيل المستخدم أو إعادة تعيين كلمة مروره أو إبطال جلساته يلغي جلساته عبر `session_version`.
- الأدوار الحالية افتراضية وثابتة، ولا توجد صلاحيات إضافية مخصصة لكل مستخدم خارج دوره.

## مسارات API الرئيسية

كل المسارات تحت `/api` تعيد `Cache-Control: no-store`. كل عمليات `POST/PATCH/DELETE` تتطلب `Origin` مطابقًا أو ترويسة `X-Requested-With: XMLHttpRequest`.

| المجموعة | مسارات مختارة |
| --- | --- |

## الضوابط الأمنية والبيانات

- كلمات المرور: scrypt بملح عشوائي، وسياسة طول لا تقل عن 10 مع حرف ورقم، ومنع اسم المستخدم واسم النظام والكلمات الشائعة.
- الجلسات: رمز عشوائي 256-bit يُخزّن كبصمة فقط، مهلة خمول 45 دقيقة، حد أقصى 12 ساعة، «تذكرني» 7 أيام، وإبطال جماعي عبر `session_version`.
- الدخول: رسائل موحّدة، مقارنة زمنية متساوية، قفل 15 دقيقة بعد 5 محاولات، وحد 30 محاولة فاشلة لكل IP خلال 15 دقيقة.
- CSRF: التحقق من المصدر لكل الطلبات المغيّرة، ورفض الطلبات بلا مصدر أو ترويسة XHR. ملف الجلسة `SameSite=Lax` و`httpOnly` و`Secure` عند HTTPS.
- الرؤوس: Helmet مع CSP صارمة، `frame-ancestors 'none'`، `Referrer-Policy: no-referrer`، و`Permissions-Policy` مقيّدة، وإخفاء `X-Powered-By`. HSTS في الإنتاج فقط.
- عزل الفروع: يُبنى نطاق كل استعلام في SQL من فروع المستخدم، ويُعاد التحقق عند القراءة والكتابة وعند فتح مرفقات أي كيان.
- التحقق من المدخلات: مخططات zod لكل الحقول، وحدود حجم للطلبات (100 كيلوبايت لـ JSON و2 ميجابايت للمرفقات و5 ميجابايت لاستيراد Excel).
- المعاملات: حفظ كشوف التحضير، اعتماد الإجازات المرتبط بالحضور، إنشاء الموظف من طلب تعيين، واستقطاع السلف عند اعتماد الراتب كلها داخل معاملات قاعدة بيانات.
- الاستيراد: التحقق من كل الصفوف أولًا، رفض الملف كاملًا عند وجود أي خطأ، فحص تكرار الرقم الوظيفي والرقم الوطني داخل الملف وفي قاعدة البيانات، والتحقق من الفرع النشط ونطاق الصلاحية والقسم.
- الاعتماد المالي: لا يُسجَّل استقطاع قبل الصرف، ولا يتجاوز مجموع الاستقطاعات قيمة السلفة، ويُقفل سجل الراتب بعد الاعتماد في الخادم والواجهة.
- منع التكرار: فهرس فريد على `(payroll_record_id, advance_id)` يمنع ترحيل الاستقطاع مرتين لنفس الراتب والسلفة.
- الحذف المنضبط: الحذف النهائي يتطلب `records.delete`، ويُرفض بـ409 عند وجود سجلات مرتبطة مع تعدادها في الاستجابة، ويُنظّف المرفقات وطلبات الاعتماد داخل معاملة واحدة. حذف المستخدم ناعم (`deleted_at`) ويستبدل اسم الدخول ويُلغي الجلسات وارتباطات الفروع. كل حذف يُسجَّل في التدقيق بدرجة `warning` أو `critical`، ويبقى سجل التدقيق محفوظاً بعد حذف الفرع مع احتفاظه بمعرّف الفرع التاريخي.
- المرفقات: أنواع مسموحة فقط (PDF، PNG، JPEG، WebP، DOCX، XLSX)، حد 2 ميجابايت، وتُخزّن داخل قاعدة البيانات وتُدقّق عمليات رفعها وحذفها.
- التدقيق: أحداث الدخول والفشل والقفل وتغيير كلمات المرور وإدارة المستخدمين والفروع والموظفين والتحضير والإجازات والسلف والتحويلات والموظفين الجدد والرواتب والتقارير والإعدادات والمرفقات. مشغّلات قاعدة البيانات تمنع `UPDATE` و`DELETE` و`TRUNCATE` على `audit_logs`.
- لا توجد أسرار افتراضية: قاعدة جديدة تبدأ بلا مستخدمين، وأداة التهيئة تعمل مرة واحدة فقط. احمِ مخرجات الطرفية لأنها قد تُسجَّل في سجلات الحاوية.

### حدود يجب معرفتها

- حماية سجل التدقيق بالمشغّلات تمنع التعديل عبر التطبيق، لكن مالك قاعدة البيانات يمكنه تعطيل المشغّلات. استخدم في الإنتاج حسابًا تشغيليًا غير مالك، واحمِ النسخ الاحتياطي.
- لا يوجد منع عام للاعتماد الذاتي كما ذُكر أعلاه؛ الاعتماد يفترض فصل الأدوار تشغيليًا.
- بعض محاولات المخالفة المنطقية (مثل تجاوز رصيد السلفة أو تعديل سجل معتمد) تُعاد كأخطاء عمل 400/409 ولا تُسجَّل كلها كأحداث تدقيق مستقلة؛ الأحداث الناجحة ورفض صلاحيات المسار هي المسجلة.
- لا توجد MFA أو إدارة جلسات مرئية لكل جهاز أو فتح حساب مقفل يدويًا.
- الأدوار ثابتة، والصلاحيات المخصصة لكل مستخدم غير مدعومة.
- الطباعة تعتمد على حوار المتصفح؛ لم يُختبر إخراج PDF من خادم أو طابعة حقيقية.

## النشر الإنتاجي الموصى به

### الخيار المختار

- **الخادم:** VPS واحد بنظام Ubuntu 24.04، بمواصفات 2 vCPU و4 GB RAM و40 GB NVMe. الموصى به **Hetzner Cloud CX22** (Falkenstein أو Nuremberg) مع تفعيل النسخ الاحتياطي اليومي للخادم. البديل الأسهل: DigitalOcean Basic 2 GB / 2 vCPU / 50 GB في Frankfurt أو Amsterdam.
- **قاعدة البيانات:** PostgreSQL 17 داخل Docker على الخادم نفسه، على شبكة داخلية غير منشورة للإنترنت. الانتقال إلى PostgreSQL مُدارة ممكن لاحقًا دون تغيير الكود.
- **HTTPS:** Caddy 2 مع شهادة Let's Encrypt تلقائية وتجديد تلقائي.
- **التكلفة المتوقعة:** 6–12 دولارًا شهريًا للخادم، إضافة إلى سعر النطاق.
- **النطاق:** اسم مثل `hrms.example.com`، وسجل DNS من النوع A يشير إلى IP الخادم. إن استُخدم Cloudflare، اجعله DNS only حتى تصدر الشهادة.

السبب: المشروع يملك `Dockerfile` وCompose جاهزين، والبيانات الحقيقية تبقى تحت سيطرة مالك النظام. المنصات المُدارة تتطلب تعديلات نشر إضافية وقد ترفع التكلفة، بينما VPS واحد مع Caddy هو أقصر مسار آمن.

الملفات الجديدة: `docker-compose.prod.yml` و`deploy/Caddyfile` و`.env.production.example` و`deploy/backup.sh` و`deploy/restore-verify.sh`، مع أدوات `export:data` و`import:data` و`cleanup:demo`.

**حالة التحقق:** صُيغت هذه الملفات ورُوجعت منطقيًا، لكن صورة Docker وCompose وCaddy لم تُبنَ أو تُشغّل في بيئة المراجعة لعدم توفر Docker، ولم يُنشأ خادم فعلي بعد. لا تعتبرها منشورة حتى تنفّذ الخطوات على الخادم وتتحقق من HTTPS والدخول والنسخ الاحتياطي.

### ما يلزم لإكمال النشر

1. خادم VPS أو حساب استضافة مع صلاحية SSH بالمفتاح.
2. اسم نطاق وصلاحية تعديل DNS.
3. عنوان IP للخادم.

لا ترسل كلمات المرور أو المفاتيح في محادثة. تُنشأ الأسرار على الخادم أو عبر مدير أسرار.

### 1. تجهيز الخادم

على Ubuntu 24.04 وبعد الدخول بمفتاح SSH:

```bash
apt update && apt upgrade -y
apt install -y ca-certificates curl ufw unattended-upgrades
install -m 0755 -d /etc/apt/keyrings
curl -fsSL https://download.docker.com/linux/ubuntu/gpg -o /etc/apt/keyrings/docker.asc
chmod a+r /etc/apt/keyrings/docker.asc
echo "deb [arch=$(dpkg --print-architecture) signed-by=/etc/apt/keyrings/docker.asc] https://download.docker.com/linux/ubuntu $(. /etc/os-release && echo $VERSION_CODENAME) stable" \
  > /etc/apt/sources.list.d/docker.list
apt update
apt install -y docker-ce docker-ce-cli containerd.io docker-buildx-plugin docker-compose-plugin
systemctl enable --now docker
ufw allow OpenSSH
ufw allow 80/tcp
ufw allow 443/tcp
ufw allow 443/udp
ufw --force enable
dpkg-reconfigure -plow unattended-upgrades
```

بعد التأكد من نجاح الدخول بالمفتاح، عطّل دخول كلمة المرور لـSSH واجعل root يدخل بالمفتاح فقط. لا تفعل ذلك قبل اختبار المفتاح حتى لا تفقد الوصول.

أنشئ سجل DNS من النوع A للنطاق إلى IP الخادم قبل تشغيل Caddy.

### 7. النسخ الاحتياطي والاستعادة

ثبّت أدوات النسخ الاختيارية:

```bash
apt install -y age rclone
age-keygen -o /root/batawil-backup.key
chmod 600 /root/batawil-backup.key
grep '^# public key:' /root/batawil-backup.key
```

احفظ المفتاح الخاص خارج الخادم (نسخة offline)، ثم أنشئ `/etc/batawil-backup.env` بصلاحية 600:

```bash
BACKUP_DIR=/var/backups/batawil
KEEP_DAYS=30
BACKUP_AGE_RECIPIENT=age1...   # المفتاح العام من الأمر السابق
# BACKUP_RCLONE_REMOTE=batawil-crypt:hrms
ENV_FILE=/opt/batawil/.env.production
COMPOSE_FILE=/opt/batawil/docker-compose.prod.yml
```

أضف مهمة يومية:

```bash
( crontab -l 2>/dev/null; echo '15 2 * * * cd /opt/batawil && set -a && . /etc/batawil-backup.env && set +a && /bin/bash deploy/backup.sh >> /var/log/batawil-backup.log 2>&1' ) | crontab -
```

شغّل نسخة أولى يدويًا وتحقق:

```bash
cd /opt/batawil
set -a && . /etc/batawil-backup.env && set +a
bash deploy/backup.sh
ls -lh /var/backups/batawil
```

- السكربت يتحقق من قراءة أرشيف `pg_dump` قبل اعتماده.
- عند ضبط `BACKUP_AGE_RECIPIENT` تُشفّر النسخة، ويُحذف ملف `pg_dump` غير المشفّر.
- عند ضبط `BACKUP_RCLONE_REMOTE` تُنسخ النسخة والبصمة إلى تخزين خارجي. يُفضّل remote من نوع crypt.
- النسخ تحتوي بيانات موظفين ومرفقات وتجزئات كلمات مرور وسجل تدقيق؛ لا تشاركها.

اختبار الاستعادة على قاعدة مؤقتة دون لمس الإنتاج:

```bash
# إن كانت النسخة مشفرة، فكّها على جهاز موثوق ثم انقلها مؤقتًا:
age -d -i batawil-backup.key -o batawil.dump batawil-TIMESTAMP.dump.age
scp batawil.dump root@SERVER_IP:/root/
```
